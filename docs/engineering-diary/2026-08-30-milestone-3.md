# Engineering Diary: Milestone 3 Automatic Monitoring

Date: 2026-08-30

## Goal

Move VakeVahti from a manually demonstrated source scan toward an operational, automatically triggered funding-monitoring product while preserving a clean future integration boundary with Vaketomate.

## Changes

- Added a reusable source-ingestion application service.
- Added persisted source-run audit lifecycle: RUNNING, SUCCEEDED, FAILED.
- Added trigger classification for CLI, API and scheduled execution.
- Added one-shot and single-replica interval worker modes outside the FastAPI process.
- Added PostgreSQL per-source transaction advisory locking to serialize overlapping persistence.
- Added migration and PostgreSQL integration tests for scan audit and concurrency behavior.
- Added Vaketomate extraction-ready integration contract and ADRs.
- Added security baseline, worker runbook, and continuously maintained interview/lesson bank.

## Key decisions

The FastAPI process does not own scheduling. A separate worker invokes the same business ingestion service used by other triggers. This prevents API replica count from becoming scheduler replica count.

VakeVahti remains independently runnable. Vaketomate will later consume or host it through published contracts rather than direct access to funding internals.

A transaction-scoped PostgreSQL advisory lock serializes persistence per source. This supplements database uniqueness constraints by making concurrent baseline/version calculations deterministic.

## Validation

The original Milestone 3 tree was validated by Backend CI with Ruff, strict mypy, Alembic migration application and PostgreSQL integration tests. This diary commit intentionally triggers CI again after rebasing the milestone branch onto the newly merged Milestone 2 main branch.

## Follow-up

Next backend slice: persisted read APIs and source-health endpoints so the real employee-facing UI can read database state rather than relying on a live demo scan.
